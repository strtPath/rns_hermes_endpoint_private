# Turn lifecycle notes for rns_hermes_endpoint

Sections:
1. INBOUND: message receipt, source_hash peer identity, ACL enforcement, active peer recording
2. CONCURRENCY: threading model, synchronization primitives, same-peer vs different-peer collisions
3. TURN: HermesClient.chat() phase order, background thread work
4. OUTBOUND: push_reply vs send_reply, downlink sequencing, acks, retry, pacing
5. CLARIFY: clarify delivery, answer capture (capture_clarify_answer, arm_clarify_wait, _clarify_pending), prompt injection
6. FAILURE MODES: child death, timeout, approval denial, empty output, _deny_veto, liveness guard

## 1. INBOUND

- The LXMF delivery callback is `LXMFBridge._on_lxmf_message`, registered in `start()` via `self.router.register_delivery_callback(self._on_lxmf_message)` (bridge.py:312; callback body bridge.py:427-465). It runs in the RNS event loop thread.
- Peer identity: `source_hash = RNS.prettyhexrep(message.source_hash)` (bridge.py:435); a lowercase-hex form `source_hash_raw` is also derived (bridge.py:436-439) and handed to the worker. `message.signature_validated` is logged but not enforced here (bridge.py:441); signature/stamp trust is delegated to the LXMF router (`enforce_stamps` passed at bridge.py:287-290).
- The raw sender `RNS.Destination` is captured as `source_identity = getattr(message, "source", None)` (bridge.py:457) and passed through to the worker for outbound use.
- The message is classified by `ChannelMetrics.from_lxmessage(message)` then `self.profiler.classify(metrics)` into a profile (bridge.py:453-454); the profile drives truncation/splitting and pacing.
- ACL enforcement is NOT in the bridge. It happens inside the handler chain built in cli.py: `handle_message` calls `acl.is_allowed(source_hash)` first; on denial it returns `"⛔ Access not authorized."` which is then sent back as a normal reply (cli.py:312-315). The ACL logic itself lives in acl.py: `AccessControl.is_allowed` (acl.py:76-103) normalizes the hash, applies blocklist first (acl.py:90-92), then `allow_all` (acl.py:95-96), then the allowlist (acl.py:99-100); default mode is deny-by-default allowlist (`HERMES_RETICULUM_ALLOW_ALL` defaults to false, acl.py:34-38).
- The active peer is recorded in the handler, not the bridge: `hermes.set_active_peer(source_hash)` (cli.py:320), stored as `HermesClient._active_peer` (hermes_client.py:427-435). The same handler also registers the per-turn push target: `mesh_push[hermes.session_name] = {"hash": source_hash, "ident": RNS.Destination(ident, OUT, SINGLE, "lxmf", "delivery")}` after recalling the peer's identity (cli.py:322-334).

## 2. CONCURRENCY

- Inbound work is fan-out into a `ThreadPoolExecutor(max_workers=_MAX_HANDLERS)` with `_MAX_HANDLERS = 4` and thread prefix `lxmf-handler` (bridge.py:28-29, 322-325). Each message is submitted as `self._pool.submit(self._process_and_reply, source_hash_raw, content, profile, source_identity)` (bridge.py:456-460). The RNS callback thread itself never blocks on Hermes.
- The worker `_process_and_reply` calls the handler, then `prepare_reply(reply, profile)` and sends each part with an inter-part `time.sleep(profile.send_delay_ms / 1000)` (bridge.py:467-483).
- Outbound pacing is serialized per recipient by `DownlinkTracker`, a `threading.Lock` guarding `_last_send`, `_outbound`, `_next_seq`, counters (downlink.py:100-112). The lock is held only for brief state reads/writes, never across the sleep (downlink.py:88-95, 157-166).
- Two simultaneous messages, different peers: independent pool workers run in parallel; each has its own `mesh_push` entry keyed by `hermes.session_name` (cli.py:326) and its own pacing clock in `_last_send[recipient_hex]` (downlink.py:157-166), so they do not block each other.
- Two simultaneous messages, same peer: both workers share one `HermesClient` session and one pacing clock. `set_active_peer` and `_active_peer` are plain attribute writes with no lock, so a second inbound message can overwrite the shared peer mid-turn; this is why the step watcher takes `turn_peer` as a parameter captured at chat() start instead of reading `_active_peer` (hermes_client.py:662-667). Pacing serializes the sends between chunks (downlink.py:147-166).
- The clarify gate is also shared state (`_clarify_pending`, `_clarify_source`, `_clarify_deadline`, `_clarify_answer` at hermes_client.py:535-549, 557-568) with no lock; it is single-valued, so only one open question exists at a time.
- Other named primitives: `StepThroughManager._lock` (bridge.py:70), `_announce_lock` + `threading.Event` `_announce_timer_stop` for the re-announce timer swap (bridge.py:219-223, 371-387), `BridgeLiveness._lock` (bridge_liveness.py:117), and the control-server HTTP server for approve/deny/stop/steer (cli.py:208-296).

## 3. TURN

- Entry: the worker calls `hermes.chat(prompt)` (cli.py:366, or cli.py:349-351 for clarify-answer turns). `HermesClient.chat` is at hermes_client.py:1287.
- Phase order inside chat(): (1) resolve/adopt the session id (`new_session` handling, session id resolution via state.db), (2) capture `turn_peer` from `_active_peer` and start the `_run_step_watcher` daemon thread (hermes_client.py:644-689) which polls state.db for new tool rows and pushes per-step messages (and the clarify question) to the peer, (3) start the liveness/turn-alive machinery, (4) spawn the `hermes chat -q` CLI child process and read its output until completion/timeout via `_run_with_liveness_guard` (hermes_client.py:1542), (5) post-processing: session adoption recap anchor, `pop_clarify_answer()` injects any captured clarify answer as a prompt prefix for the follow-up (see section 5), empty-output handling, guard-kill/retry logic (`_guard_kill_worth_retrying`, hermes_client.py:1269), then return the final answer string.
- Background thread work inside `_run_with_liveness_guard`: two daemon reader threads drain the child's stdout and stderr into lists, touching a liveness clock under `activity_lock` (hermes_client.py:1560, 1570-1581, 1669-1676); a `hermes-liveness` watchdog daemon thread enforces `turn_hard_cap` (absolute wall clock) and `liveness_timeout` (silence window) and can kill the child (hermes_client.py:1583-1646); the main worker thread blocks on `proc.wait()` (hermes_client.py:1685). The step watcher thread (hermes_client.py:644+) pushes tool call + output chunks via `self._push_callback` (wired to `bridge.push_reply` in cli.py:284-291) and the clarify question.
- `HermesClient.stop()` / `is_running()` / `pause()` / `resume()` are at hermes_client.py:1798/1838/1851/1872 and are used by `_deny_veto` and the stop command.

## 4. OUTBOUND

- `Bridge.push_reply(recipient_hex, text, source_identity, chunk=True, max_chars=STEP_CHUNK_CHARS)` (bridge.py:239-271) is the multi-part, paced, tagged path: it splits with `split_message` (adapter.py:42-70), tags multi-part pushes with a per-push tag via `downlink.next_push_tag()` and prefixes `[pN i/N]` via `sequence_chunks` (downlink.py:54-84, 193-197), paces BEFORE each non-first send with `downlink.pace_wait(recipient_hex, MIN_CHUNK_INTERVAL_MS)` (bridge.py:264-268, downlink.py:147-166), and delegates each part to `send_reply`. Used for step pushes and full step dumps (cli.py:268, 289).
- `Bridge.send_reply(recipient_hex, text, source_identity)` (bridge.py:485-571) is the atomic single-message send: resolves the recipient identity (source_identity or `RNS.Identity.recall`, with an 8x1s `request_path` wait when unknown, bridge.py:497-529), allocates a seq BEFORE the send with `downlink.next_seq()` (bridge.py:533), builds a direct `LXMF.LXMessage` with `include_ticket=True` and registers a per-chunk delivery callback `_on_outbound` (bridge.py:544-553), calls `self.router.handle_outbound(lxm)`, and only on success calls `downlink.record_send(recipient_hex)` + `downlink.register_dispatch(seq, recipient_hex)` (bridge.py:557-558). The final answer to a turn is sent through this path: `_process_and_reply` sends each prepared part via `self.send_reply(source_hash, part, source_identity)` (bridge.py:473-478).
- Sequencing: monotonic `_next_seq` per message (downlink.py:118-133); multi-part pushes additionally carry `[pN i/N]` tags so a dropped tail is visible (downlink.py:54-84).
- Acks: `_on_outbound(seq, recipient_hex, lxm)` fires on the RNS event loop thread, maps LXMF state to outcome via `_STATE_MAP`/`_STATE_OUTCOME` (SENT=propagated, DELIVERED=delivered, FAILED=failed; downlink.py:23-38) and calls `downlink.note_outcome(seq, outcome)`, which is idempotent (pops the seq once) (bridge.py:573-592, downlink.py:178-187).
- Retry: there is no automatic resend. Silent loss is detected lazily: `next_seq()` runs `_sweep_timeouts_locked()` which counts any seq without a callback within `ACK_TIMEOUT_S` (default 300s) as `timeout` (downlink.py:16, 118-126, 215-229).
- Pacing: per-recipient last-successful-send clock; `pace_wait` sleeps only if less than `MIN_CHUNK_INTERVAL_MS` (default 500ms) elapsed, and a failed send does not consume budget because `record_send` is called only after success (bridge.py:556-557, downlink.py:147-172).

## 5. CLARIFY

- Delivery: the step watcher (hermes_client.py:644+) detects a `clarify` tool call. In the normal path `_push_step` routes it to `_push_step_clarify` (hermes_client.py:599-605), which formats the question with numbered choices via `_format_clarify` (hermes_client.py:468-507), pushes it to the peer via `_push_callback` (i.e. `bridge.push_reply`), and ONLY arms the gate if delivery succeeded: `arm_clarify_wait(source_hash)` (hermes_client.py:616-642).
- `arm_clarify_wait` (hermes_client.py:557-572) sets `_clarify_pending = True`, `_clarify_source = source_hash`, `_clarify_deadline = now + CLARIFY_ANSWER_TIMEOUT_S` (env `HERMES_MESH_CLARIFY_TIMEOUT`, default 3600s, hermes_client.py:464-466).
- Capture: on the next inbound message, `cli.handle_message` calls `hermes.capture_clarify_answer(content, source_hash)` BEFORE command dispatch (cli.py:343-352). It returns the text only if `_clarify_pending` is set, the deadline has not passed (stale guard clears the gate, hermes_client.py:529-534), and the sender matches `_clarify_source` (ownership guard, hermes_client.py:537-543). On success it clears the gate and stores `_clarify_answer = text` (hermes_client.py:544-549).
- Injection: the handler then starts a turn with the prompt `"The user answered your earlier question. Continue."` (cli.py:349-351); inside `chat()`, `pop_clarify_answer()` (hermes_client.py:551-555) returns and clears the stored answer and it is injected as a prefix into the prompt sent to the (still-waiting) agent, the same prefix path `/steer` uses (cli.py:336-342).

## 6. FAILURE MODES

- Child death: `_run_with_liveness_guard` blocks on `proc.wait()` then inspects `proc.returncode` (hermes_client.py:1685, 1698-1713). A deliberate stop/veto (`_stop_requested` without `_guard_killed`) returns the honest `⏹️ Stopped before the turn finished.` (hermes_client.py:1704-1707). A guard-kill sets `_last_run_ms` (hermes_client.py:1696) and the caller `chat()` retries exactly once ONLY when the child died early in the window (`_guard_kill_worth_retrying`: run_ms < liveness_timeout, hermes_client.py:1269, 1455-1493): it sleeps 5s, re-resolves the session and re-spawns the same prompt under a fresh turn-alive generation (`bump_turn_alive_gen()`, hermes_client.py:1489-1493). If the child ran a FULL window before the guard fired, no retry: a resume would re-burn the window and fail identically, so it reports `⏱️ Turn ran past the liveness window...` (hermes_client.py:1494-1512). `_guard_killed=True` always clears `_deny_veto` on kill (hermes_client.py:1597-1599, 1618-1625) so a liveness kill never masquerades as a mesh veto that would suppress the retry.
- Mesh veto: `stop()` (hermes_client.py:1798) sets `_stop_requested=True`, `_guard_killed=False`, `_deny_veto=True`, then `_kill_process()` (hermes_client.py:1780-1796) kills the Popen and clears the turn-alive marker.
- `_deny_veto` (cli.py:55-87) is the abort choke point for mesh-operator denial (ControlServer POST /step kind='gate' on_deny, or the pre-exec mesh-tool-gate plugin): it is a loop guard, no-op unless `hermes.is_running()` (cli.py:71-79), otherwise it calls `hermes.stop()` to kill the in-flight child (cli.py:80-87); `ctrl.on_deny` is wired to it (cli.py:209).
- Timeout: `HERMES_TIMEOUT` (default 300s, cli.py:167) bounds the child; downlink `ACK_TIMEOUT_S` (default 300s, downlink.py:16) bounds outbound acks; clarify `CLARIFY_ANSWER_TIMEOUT_S` (default 3600s, hermes_client.py:464-466) bounds the answer wait; the child watchdog enforces `liveness_timeout` silence plus an absolute `turn_hard_cap` (hermes_client.py:1583-1602); gate timeouts `MESH_GATE_TIMEOUT` / `HERMES_MESH_APPROVAL_TIMEOUT` are validated at startup (`_validate_gate_timeouts`, cli.py:90-153) to fail loudly on misconfiguration.
- Approval denial: see `_deny_veto` above; a pre-exec block is handled by the plugin returning a block directive (not by killing the child).
- Empty output: if the child exits 0 with no stdout, the guard returns `_(no response)_` (hermes_client.py:1723-1726); for clarify-answer turns the handler falls back to `"✅ Answer received."` (cli.py:352); for normal turns `prepare_reply` returns `[]` on empty text (adapter.py:115-116) so nothing is sent, and `send_reply`/`push_reply` return False on empty text (bridge.py:253-254, 493-495).
- Liveness guard: two layers. (a) Per-turn: the `hermes-liveness` watchdog daemon (hermes_client.py:1583-1646) enforces an absolute `turn_hard_cap` wall clock (hermes_client.py:1591-1602) and a `liveness_timeout` silence window (hermes_client.py:1603-1628); a fresh per-session turn-alive marker (written at spawn with phase='model', hermes_client.py:1652-1659; refreshed on tool progress via `write_turn_alive_marker`, hermes_client.py:261-285, e.g. cli.py:865 path) keeps a slow-but-working model alive by touching the clock (hermes_client.py:1629-1646). (b) Bridge-level: `BridgeLiveness` (bridge_liveness.py:94+) runs a daemon thread that probes RNS via `RNS.Transport.interface_last_jobs` (default probe, bridge_liveness.py:51-68, max age 30s). On healthy it writes the heartbeat marker and pings systemd `WATCHDOG=1`; on a wedged RNS (or total GIL freeze) it STOPS pinging so systemd's `WatchdogSec` fires and restarts the bridge (bridge_liveness.py:169-183). Started in `run_forever()` after announce (bridge.py:623-627) and stopped in `stop()` (bridge.py:604-605).
