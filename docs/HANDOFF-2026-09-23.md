# Handoff: Session of 2026-09-23

nothing is inference presented as fact.

## 1. The headline finding

**The bridge may not need to exist in its current form.**

Hermes' gateway supports messaging platforms through an adapter interface. Telegram, Matrix
and WhatsApp are not core code; they are plugins. An adapter implements four abstract methods
(`connect`, `disconnect`, `send`, `get_chat_info`), calls `self.handle_message(event)` when a
message arrives, and inherits everything else: session handling, tool-call streaming, the
clarify round trip, approval prompts, slash commands, memory, persistence.

Out-of-tree registration is the documented recommended path. `ADDING_A_PLATFORM.md` states it
"requires zero changes to core Hermes code", and `gateway/run_adapters.py::_instantiate_adapter`
checks the plugin registry before built-ins.

Consequence: Reticulum could be a platform plugin in this repo, loaded by the gateway the same
way Telegram is. No PR into Hermes needed. No bridge process spawning children.

## 2. Why the current design struggles

The bridge drives the Hermes CLI in its programmatic one-shot mode while expecting interactive
behaviour. It spawns:

    hermes chat -q <message> --source <tag> -Q [--resume ID | -c NAME]

`-q` plus `-Q` (or simply having no TTY) selects Hermes' single-query path, which assumes no
human is present. In that mode Hermes installs a clarify callback that refuses to wait and
tells the model to choose for itself (`hermes_cli/cli_agent_setup_mixin.py:14`, issue #94943).

So a mesh clarify question is pushed, a gate is armed, the answer is captured, and it is
injected into a turn that already finished. Every step works; the outcome is wrong.

Everything the bridge hand-built exists because it sits outside the gateway: session adoption
heuristics, a step watcher polling `state.db`, a clarify gate, an approval control server, a
downlink queue. The gateway already has all of these, implemented and proven.

## 3. The intended model, stated

Recorded from the user directly, and it is the target to design against:

The bridge should interact with the CLI the way a person does at a terminal. When the agent
needs a decision mid-task, the task is *held open* while the user answers, then continues from
where it was. Live view of tool calls matters, for visibility and so a turn can be
interrupted. Interruption is best effort, not guaranteed, because mesh latency may deliver the
abort late. Seeing the work is the primary value.

Current reality: three of those four properties are missing. Only live view works.

## 5. Corrections made today

Several things previously believed were wrong, and are now corrected in the docs and in memory:

- The clarify timeout is not a timeout. No timeout value would have fixed it. Raising
  `approvals.timeout` would have done nothing.
- `HERMES_MESH_CLARIFY` defaults to ON (`"1"`), not off.
- The gate ordering is `MESH_GATE_TIMEOUT >= HERMES_MESH_APPROVAL_TIMEOUT` (plugin window at
  least as long as the control server's), not the reverse.
- `plugins.hook_callback_timeout` is 490 in this deployment, code default 30.
- The endpoint serves any model name asked of it (llama.cpp does not validate), so model-name
  mismatch was never the cause of the stalled test. It was the clarify callback returning
  instantly.

## 6. The open question for the next session

**Does Reticulum fit the platform-adapter model?**

ANSWERED, 2026-09-24, then REVISED the same day once the source was read. See
`spec-feasibility-reticulum-platform.md` (revised) and the evidence in
`_notes-delivery-confirmation.md`. The short version:

It fits for messaging, and the delivery problem is NARROWER than first stated. RNS and LXMF do
report per-message delivery, and for direct delivery the signal is bounded and honest.

Direct delivery. `RNS.PacketReceipt` sets `DELIVERED` only when a cryptographic proof from the
destination validates (Packet.py:495-538). `LXMessage.__mark_delivered()` then fires the
delivery callback (LXMessage.py:561-571). Failure is reported too: after
`MAX_DELIVERY_ATTEMPTS = 5` (LXMRouter.py:30) with `DELIVERY_RETRY_WAIT = 10s` between attempts,
`fail_message()` sets `FAILED` and calls `failed_callback` (LXMRouter.py:2564-2571). That maps
onto `SendResult` honestly.

Propagated delivery is where the gap actually is. Handing a message to a propagation node fires
`__mark_propagated()` with `state = SENT`, not `DELIVERED` (LXMessage.py:573-583). The node
stores it in `propagation_entries` until a peer syncs. No per-message signal reaches the original
sender, ever. The gateway would record that as delivered.

So the structural problem is real but scoped: the gateway has no queued-or-pending state, so
UNBOUNDED delivery has no honest representation. That is the propagated case, not all of
Reticulum.

Correction to what this handoff first said: "there is no callback from RNS to the gateway when a
queued message is finally delivered or dropped" was wrong as an absolute. The callbacks exist and
fire. Also corrected: `Packet.send()` returns `False` immediately when no path exists
(Packet.py:307-313, traced through `Transport._outbound` returning `sent = False`), so there is
no silent queue at the packet layer; queueing lives in `LXMRouter`.

Also strained: `connect()` cannot distinguish "RNS is up" from "peers are reachable", so peer
outages never trigger the reconnect watcher. Chat ids survive only until a peer rotates keys.

What fits: destination hashes as chat ids, `dm` as the chat type, inbound via
`handle_message`, adapter-owned threads, and async bridging via a background thread feeding an
asyncio queue.

What now gates the design, replacing the old experiment: does this deployment deliver directly or
through a propagation node? Direct means the adapter is a translation and the complexity is
deleted. Propagated means the adapter owns a delivery ledger for the node-to-peer leg, and that
ledger is the design work.

## 9. Working practice that mattered

Subagents against a local model need three things or they fail silently and produce nothing:
one child at a time (they starve each other), an output file they append to every few file
reads (do not let them research broadly then write at the end), and a scope of one subsystem.
Splitting gather from compose is what made today's research work. See the
`local-model-subagents` skill.

Verify before asserting. Three of the corrections in section 5 were caught by subagents
checking source against notes that had been repeated for weeks. The notes were wrong; the code
was right.
